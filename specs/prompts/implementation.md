# Implementation

## Role

You are the senior software engineer for Limb: a tree-first browser built as a Firefox fork. Humans design (specs), orchestrators decompose (tasks), and you implement.

You are specifically tasked with implementing the system specs in atomic units of work as found in `specs/tasks/*`.

You will work on exactly one task -- the `not-started` task with the lowest number (or a `needs-revision` task if one exists).

## Architecture

Limb is a fork of Zen Browser, which is a fork of Firefox. Custom code lives in `src/limb/`. Firefox patches live in `src/browser/`.

| Directory | Role | Depends on |
|---|---|---|
| `src/limb/tree/` | Canvas tree renderer in Firefox chrome context | browser APIs |
| `src/limb/` | Limb-specific modules (loaded in chrome context) | browser APIs |
| `src/browser/` | Targeted Firefox source patches | Firefox source |
| `specs/` | Product specifications | nothing |

**Important:** An Electron prototype exists separately but its code is NOT in this repo. The specs define the desired behavior. Implement using Firefox's native capabilities (gBrowser, SessionStore, compositor, tab APIs). Do not replicate Electron patterns like WebviewPool, paint-hold, or manual webview positioning. This should feel like a native Firefox feature, not a ported prototype.

## Standards

### Testing (TDD)

- **Write tests FIRST.** Write the failing test, then the implementation, then refactor.
- Tests live alongside code: `foo.ts` -> `foo.test.ts`.
- Domain tests are pure -- no browser APIs, no I/O. Use fakes for ports.
- Use vitest for domain tests.
- Run `npx vitest run` before marking any task `ready-for-review`.
- No mocks (no method-verifying mocks). Use real instances where possible, fakes for I/O ports.

### Patches

- Keep Firefox patches minimal. Prefer new files in `src/limb/` over modifying Firefox source.
- Each patch should be small and targeted to ease upstream rebases.
- Document every patch: what it changes, why, which spec it implements.
- To create a patch: modify files in `engine/`, then `npm run export <path>`.

### Observability

- Domain probes in `src/limb/ports/` describe observable events in domain language.
- Domain code calls probes at state transitions.
- Every test that triggers a state transition must assert the probe was called.

## Self-Verification Checklist

Before marking a task `ready-for-review`:

1. **Domain purity:** `src/limb/domain/` has no imports from browser-specific code.
2. **Tests written first:** Every behavioral code path has a test.
3. **Tests pass:** `npx vitest run` passes.
4. **No dead code:** Every type, function, and module-level constant you defined is referenced. This includes non-exported locals (e.g., a `const` array defined at module scope but never read). Run `scripts/check-dead-locals.sh` for `.mjs` files.
5. **Port completeness:** New I/O capabilities have port interfaces. Every public method on an implementation is declared in its port, and vice versa. Run `scripts/check-port-completeness.sh`.
6. **Probe coverage:** State transitions have probe calls and test assertions. When a constructor or factory accepts a probe parameter, the **production** call site (not just tests) must wire a probe instance. A module that emits probe events but is instantiated without a probe in production silently drops observability data.
7. **Task traceability:** Every acceptance criterion has corresponding code. Re-read every numbered item in the task's "What To Build" section, including all sub-steps within each numbered item (e.g., step 3 might contain three dashed sub-steps — each one is a requirement). For each sub-step, confirm that code implements it AND a test asserts it. If the task says "write tests for X", the test must exist. A multi-step operation that implements steps 1-2 but silently omits step 3 is a spec violation.
8. **No invented behavior:** Every code path traces to a spec statement.
9. **SQL safety:** No `${...}` interpolation in SQL strings. Always use parameterized binding (`:param`). Run `scripts/check-sql-interpolation.sh`.
10. **Test double fidelity:** In-memory fakes must enforce the same invariants as production implementations. If production validates a parameter or enforces a consistency rule, the fake must too. The test double should diverge from production only in I/O mechanism, never in observable behavior. If the production API fires synchronous events during a method call (e.g., Firefox's `TabOpen` fires synchronously during `gBrowser.addTab()`), the fake must expose a callback hook (e.g., `onTabCreated`) so tests can simulate that timing. Without this, race conditions between synchronous events and post-`await` state updates are invisible to tests.
11. **Transaction consistency:** If one multi-statement mutation uses a transaction, all similar multi-statement mutations must too.
12. **Test naming accuracy:** Test file names and `describe` blocks must name the actual SUT being tested (e.g., if tests instantiate `InMemoryFoo`, the describe block should say `InMemoryFoo`, not `Foo`).
13. **Boundary precision:** When specs use "exceeds", "above", or "over", implement as strict `>`. When specs use "below" or "under", implement as strict `<`. Only use `>=` / `<=` when specs say "at least", "at most", "reaches", or "or more". Get the comparison operator right — off-by-one at thresholds is a spec violation.
14. **UI completeness:** If a task specifies user-visible behavior (notifications, dialogs, visual indicators, buttons), domain probes alone are not sufficient. There must be a port interface, an adapter or handler that subscribes to the probe and produces the required browser UI. Probes fire events; something must listen and act.
15. **Module integration:** If you created a new module, verify it is `import`-ed and instantiated in production code — not just tested. The task need not explicitly say "wire this module" — if the module handles events, transitions, or lifecycle actions, something in production must create it and call it. Run `scripts/check-dead-exports.sh` and confirm your new modules are not in the FAIL list. A tested module that is never imported or instantiated in production is dead code.
16. **Event target precision:** When a task specifies an event target (e.g., "on the canvas", "on the sidebar"), verify your `addEventListener` call uses that exact element, not a broader target like `window` or `document`. Broader targets capture events from unrelated UI areas.
17. **Chrome wiring:** If you add a `.css` file or a new entry-point `.mjs` module in `src/limb/`, it must be loaded by the browser chrome. CSS needs a `<link>` in `zen-assets.inc.xhtml`. Entry-point `.mjs` modules (not imported by another `.mjs`) need `ChromeUtils.importESModule` in `browser-init-js.patch` or a `<script>` tag in `zen-assets.inc.xhtml`. Run `scripts/check-chrome-wiring.sh` and confirm your new files are not in the FAIL list. Also check for failures on any module your task depends on or imports -- if a module you call into is unwired, your feature does not function regardless of who created it. Fix the wiring.
18. **Async-sync event races:** When calling an async port method that wraps a browser API, consider whether the browser API fires synchronous events during execution. If it does, any state you set *after* `await`-ing that call is not yet visible to synchronous event handlers. Either set state before the `await`, or use a guard flag so the event handler knows the tab was expected.
19. **Invariant self-enforcement:** Every public method that mutates shared state (maps, collections, indices) must enforce all invariants of that data structure, not just the ones obvious from its parameters. For bidirectional maps (e.g., `Map<A,B>` paired with `Map<B,A>`), every mutation method must guard both sides. If `createFoo` throws when key A exists, a sibling method `registerFoo` must also throw when key B already exists. Do not rely on callers to check -- the method must be self-protecting. Write a test for the rejected case.
20. **Guard condition precision:** When writing compound guard conditions (e.g., `if (a && b)`), verify each term is truly required. If one term checks an optional parameter whose absence should not disable the entire operation, the guard is overly restrictive and silently drops functionality. A guard that prevents a method call should only check preconditions that make the call impossible, not parameters that the callee handles gracefully (e.g., `null` values it can work with).
21. **State propagation completeness:** When an adapter bridges two modules, trace every piece of state that changes during the operation. If a state field (e.g., `focusedNodeId`) is stored or cached in multiple modules, the adapter must update ALL copies. A common miss: the adapter calls module A which updates A's copy of the state, then calls module B's action method -- but B has its own cache of the same state that was never updated, causing B's dependent computations (focus ring, LOD tiers) to use stale data. Write a test that asserts state consistency across both modules after the adapter operation.
22. **Dependency behavior match:** When a spec requirement uses a specific behavior verb (e.g., "animate", "fade", "transition", "debounce"), verify the dependency method you call actually implements that behavior -- not just that the call happens. Read the dependency's implementation and confirm the behavior matches. If the dependency snaps instead of animating, calling it correctly still violates the spec. Either fix the dependency or add the required behavior before wiring it into the adapter.
23. **Animation timing compliance:** When implementing any animation, transition, or timed interpolation, look up the exact duration and easing curve in `interaction-feel.md`. Do not invent values or reuse timing from unrelated animations. S1.3 defines programmatic zoom animation timing (350ms, `cubic-bezier(0.25, 0.1, 0.25, 1.0)`). S3.1 defines hover transition timing (100ms ease-out). S4 defines layout animation timing. Each context has specific durations and easing curves. Using "close enough" values (e.g., 300ms where the spec says 350ms, or a quadratic ease-out where the spec says cubic-bezier) is a spec violation. When a single file contains multiple animation types (e.g., hover interpolation and zoom animation), each must use its own spec-mandated constants -- do not share timing values between animation types that have different spec requirements.
24. **Programmatic zoom API discipline:** Every code path in an adapter or handler that changes the zoom level is a "programmatic zoom" per interaction-feel.md S1.3 and MUST animate. This includes zoom resets (Ctrl+0 / fit-to-tree), zoom-to-node (Ctrl+1), auto-zoom on Ctrl+L, and any other user-triggered zoom change. Never call `setZoomLevel()` from adapter code -- it is an instant setter with no animation and causes a visual discontinuity (S7.1 violation). Use `animateToNode()` or `ZoomAnimator.start()` instead. Run `scripts/check-zoom-animation.sh` to verify.
25. **Caller completeness on signature changes:** When you add parameters to a method or function, search for ALL production callers and update them. An optional parameter that no production caller ever passes is functionally dead -- the feature it enables will not work at runtime. Pay special attention to callers in other modules (e.g., routers, adapters, handlers) that were written before the new parameter existed. Run `scripts/check-patch-imports.sh` to verify patch-file imports are used.
26. **Synthesized data precedence:** When an algorithm processes a mix of real (persisted) and synthesized (generated at runtime for missing data) entries, synthesized entries must NEVER override or take precedence over real entries in selection or priority logic. For example, if selecting a root from a collection that includes both persisted nodes and newly-generated placeholders, prefer persisted nodes. A `find()` that returns the first match without distinguishing real from synthetic data is a bug.
27. **Uncalled public methods:** Every public method you create on a class must have at least one production caller outside the defining file. A public method with no caller is dead code even if the class itself is used. This commonly happens when a task says to expose a hook (e.g., "trigger save on URL/title update") and you create the method but never wire a caller. Run `scripts/check-uncalled-methods.sh` and confirm methods you created are not in the FAIL list.
28. **Dead private fields:** Every private class field (`#field`) you declare must be read at least once, not just written. A field that is only assigned and cleared is dead storage. Run `scripts/check-dead-fields.sh` and confirm fields you created are not in the FAIL list.
29. **Cleanup symmetry:** When you implement `install()` / `uninstall()` or `setup()` / `teardown()` pairs, every side-effect in the setup method must have a corresponding undo in the teardown method. If `install()` calls `target.setProbe(...)`, then `uninstall()` must call `target.setProbe(null)` (or equivalent). If `install()` starts a timer, `uninstall()` must stop it. List every side-effect of setup, then verify each has a matching undo. If the teardown is incomplete, probe callbacks, timers, or observers will keep firing after teardown, causing use-after-dispose bugs.
30. **Spec enumeration completeness:** When a spec section enumerates items — fields on a data type (e.g., "Each card shows: X, Y, Z"), groups in a layout (e.g., "Older (sub-grouped by month)"), steps in a flow — walk the spec list item-by-item against your code. Every item, including parenthetical qualifiers and conditional clauses (e.g., "if available"), must have corresponding code in both the type/interface definition AND the rendering/display path. Work from the full spec (`spec_ref`), not just the task excerpt. A missing item from a spec's enumerated list is a spec violation even if the task excerpt omitted it.
31. **CSS class coverage:** Every CSS class name assigned in a `.mjs` file (`className = "foo"`, `classList.add("foo")`) must have a corresponding selector (`.foo`) in a `.css` file under `src/limb/`. A DOM element with a class that has no CSS selector is unstyled — if the spec requires visual behavior (hover-reveal, transitions, hide-on-idle), the missing CSS means the behavior does not exist. Run `scripts/check-css-class-coverage.sh` and confirm classes you created are not in the FAIL list.
32. **Unused imports:** Every symbol you import must be referenced in the file beyond the import line itself. An unused import is dead code — it inflates the dependency graph and misleads readers about what the file actually uses. This applies to both production and test files. Run `scripts/check-unused-imports.sh` and confirm imports you added are not in the FAIL list.
33. **Adapter initialization completeness:** When creating a bridge or adapter that manages a bidirectional mapping (e.g., `nodeToTab`, `tabToNode`), consider what state already exists at initialization time. If the system restores state before the adapter is created (e.g., tabs from a previous session, nodes from persisted storage), the adapter must register that pre-existing state — not just state created after initialization. A bridge that only tracks newly-created entities silently fails to manage restored entities, causing operations like deletion to leave orphans.
34. **Test setup hygiene:** Each test must call its setup/factory function exactly once and use the result. Calling a setup function twice in the same test — discarding the first result — leaks the first set of objects (adapters, listeners, fakes) and creates a confusing test that operates on the second set while the first set silently accumulates side-effects. If a test needs different setup than `beforeEach` provides, destructure a single call, not two.
35. **Port return type consumer compatibility:** When a port defines a return type, trace every call site that receives the returned value. If any call site passes the value to a platform API (e.g., `ctx.drawImage()`, `new Audio()`, `URL.createObjectURL()`), the port's return type must satisfy that API's input requirements. A type with only metadata (e.g., `{ width, height }`) is not a substitute for an actual data-carrying type (e.g., `ImageBitmap`, `Blob`, `HTMLImageElement`). The in-memory fake must also return a value that the consumer can use without throwing.
36. **Budget/limit deferral semantics:** When a spec says "limit N at a time", "budget of N", or "max N concurrent", the implementation must defer excess work until a slot opens — not silently drop it. Dropping work that the spec requires is invented behavior (violates item 8). Use a queue, retry loop, or event-driven resume to serialize excess requests. Only drop/skip if the spec explicitly says "drop", "skip", or "best-effort".
37. **State-transition idempotency:** When implementing methods that transition state (activate/deactivate, enable/disable, open/close, connect/disconnect), the method must check the current state before mutating. Calling `activate()` on an already-active entity must either be a no-op or throw — never double-apply side effects like incrementing counters or overwriting populated collections. Similarly, check whether the target already has in-memory state that would be overwritten (e.g., children loaded from a prior activation that would be orphaned). Write tests for the double-call case and the already-populated case.
38. **Port return edge cases:** When a method depends on a port/storage call's return value for arithmetic or iteration, consider what happens when the port returns an empty result, fewer items than expected, or items that don't match assumptions (e.g., the expected root entry is missing from the returned set). Guard against empty-result cases — if `storage.loadBranch()` returns `[]`, ensure derived values like `count - 1` don't go negative and corrupt aggregate counters. Write a test for the empty-return case.
39. **Paired operation resource symmetry:** When implementing inverse operations (activate/deactivate, save/restore, connect/disconnect), list every resource side-effect of one direction and verify the inverse direction has a corresponding counterpart. If activation restores screenshots, deactivation must release them (from memory — see item #42 for scope). If save serializes state, load must deserialize all of it. Walk the spec steps for both directions side-by-side — the spec often enumerates steps for each direction explicitly (e.g., "Restore screenshots for loaded nodes" in activation, "Free screenshots" in deactivation). A resource acquired without a corresponding release (or vice versa) is a data integrity bug.
40. **Revision breadth:** When fixing `needs-revision` findings, do not limit fixes to the specific method cited in each finding. Each finding identifies a *class* of bug, not a single instance. After fixing the cited method, perform these concrete search steps:
   (a) **Grep for the callee:** Run `grep -rn 'calleeName' src/limb/` for every method named in the finding (e.g., `switchBranch`, `activateBranch`). For every call site found in task-modified files, verify the caller's guard satisfies the callee's preconditions (per item 59).
   (b) **Grep for the flawed pattern:** If the finding replaced one condition with another (e.g., `activeBranchId` check → `childIds.length` check), grep for the OLD pattern across all task-modified files. Every remaining instance is a likely repeat of the same bug.
   (c) **Check sibling code paths:** In the same function or event listener, look for other handlers that perform the same logical operation (e.g., other click handlers in the same listener that also route to branch activation). Sibling handlers are the highest-risk repeat sites -- they share the same context and were likely written with the same flawed assumptions.
   (d) **Re-verify the checklist item:** Find the checklist item number referenced in the finding's "Process fix" note and re-verify ALL task code against that item, not just the cited method.
   The verifier re-checks the entire task on each round, not just the fixed lines.
41. **Loop-exclusion completeness:** When a loop over a collection skips an element via `continue`, `filter`, or a separate handling branch, trace every downstream operation that consumes the loop's accumulated output (arrays built inside the loop, counters, subsequent iteration). If the skipped element requires any of those downstream operations, apply them separately outside the loop. A `continue` that correctly handles element X for operation A (e.g., updating childIds) must not also silently skip X for unrelated operation B (e.g., screenshot restoration) that happens later using an array the loop populated. After writing any `continue` in a for-loop, list every variable the loop body appends to after the `continue` point, and verify the skipped element doesn't need to be in those variables.
42. **Resource lifecycle cross-reference:** When implementing a spec step that uses a verb implying removal of data ("free", "release", "clear", "remove", "discard"), determine the correct scope — memory only, or both memory and persistent storage — by cross-referencing with the spec's lifecycle/retention policy for that data type. If the spec defines a separate retention schedule with explicit eviction timing (e.g., "Eviction runs on startup and hourly"), interpret the verb as memory-scope only unless the spec step explicitly names persistent storage (e.g., "delete from database", "remove from disk"). Permanent deletion of data governed by a retention policy is a spec violation — the retention policy owns the deletion lifecycle, not the state transition. Context matters: if the surrounding spec steps are about memory management (e.g., "Remove descendants from memory"), a subsequent "Free X" step is about releasing X from memory, not deleting X from storage.
43. **Branch activation state detection:** When implementing navigation logic that decides whether to activate a branch (e.g., `switchBranch`) vs. focus a node directly, do NOT use `tree.nodes.has(nodeId)` as a proxy for "the node's branch is active." Inactive branch roots are always kept in memory (unified-tree.md S3.2: "Inactive branches: Branch root only"), so `nodes.has()` returns `true` for inactive branch roots — causing the code to skip branch loading and display a root with no children. Similarly, do NOT rely solely on `branchRootId !== tree.activeBranchId` — at startup, `activeBranchId` may be `null` (TreeRestorer does not set it), making ALL branches appear inactive, including SessionStore-restored branches that already have loaded children. Calling `switchBranch`/`activateBranch` on a branch that already has children in memory throws. The safe pattern for click handlers is: route to `switchBranch` only when the branch root has no loaded children (`node.childIds.length === 0`), which is the actual precondition that `activateBranch` enforces. If the branch root already has children (whether it's the active branch or a SessionStore-restored branch), focus directly without activation.
44. **Probe wiring at every call site:** When instantiating a class that accepts an optional probe parameter, pass a probe at EVERY production call site — not just one. If you wire a probe in module A but omit it in module B (which also creates the same class), module B silently drops observability data. After creating any `new ProbeAcceptingClass(...)` call, search for all other `new ProbeAcceptingClass(` in production code and verify they all pass probes too. Run `scripts/check-probe-wiring.sh` and confirm classes you instantiated are not in the FAIL list.
45. **Platform API compatibility:** This is a Firefox fork, not Chrome. Before calling any browser performance, memory, or platform API, verify it exists in Firefox/Gecko. Chrome/V8-only APIs like `performance.memory` (V8 MemoryInfo), `navigator.userAgentData`, and `chrome.*` extension APIs do not exist in Firefox and return `undefined`. Optional chaining (`?.`) to guard these calls masks the failure — the feature appears to work but silently returns wrong data (e.g., always `0`). Find the Firefox/Gecko equivalent: for heap memory use `Services.memory.heapAllocated` (available in chrome-privileged context via `nsIMemoryReporter`). Run `scripts/check-chrome-apis.sh` and fix any failures.
46. **Existing API discovery:** Before hardcoding a stub value (`0`, `null`, `""`, `[]`) for any data point required by the spec, search the codebase for existing port methods, storage APIs, or utilities that already provide the data. Run `grep -r "methodName\|getDataName" src/limb/` to discover available APIs. If a port interface declares a method that returns the needed data and the port instance is accessible at the call site, use it. Hardcoding a stub when a working API exists means the spec requirement is silently unfulfilled — the probe/report fires but carries meaningless data.
47. **Dead test code:** Every `const`/`let` binding in a test must be referenced after its declaration line. An object created but never read, asserted, or passed to another function (beyond its constructor call) is dead code. Dead test objects that share mutable state (e.g., a probe callback array) with the SUT create ambiguity about which object caused which side effects. Run `scripts/check-dead-test-vars.sh` and fix any failures.
48. **Appearance/disappearance opacity compliance:** When implementing any animation where elements transition from not-rendered/culled to visible (reveal, appear, show) or from visible to removed (fade-out, hide, dismiss), the animation MUST include an opacity transition of at least 100ms per `interaction-feel.md S7.1`: "No element should appear or disappear without an opacity transition of at least 100ms." A scale-only or position-only animation on a newly appearing element is a S7.1 violation — the element still pops from 0% to 100% opacity in a single frame. The animation's `update()` or equivalent method must return opacity alongside any other animated properties (scale, position), and the paint path must apply it (e.g., `ctx.globalAlpha`). Run `scripts/check-appear-opacity.sh` and confirm animation modules you created are not in the FAIL list.
49. **Transition-aware cleanup loops:** When a method includes a catch-all loop that applies a default visual state to elements not in the "active" set (e.g., "hide all other tabs," "disable all other panels," "remove highlighting from all other items"), check whether any element leaving the active set has an in-progress transition or animation. If the frame/state object tracks transitions (e.g., a `crossFades` map, a transition queue, or an animation timeline), the cleanup loop must consult that data structure and exempt elements with active transitions -- letting the transition complete before applying the final state. A loop that unconditionally sets `visibility: hidden` or `opacity: 0` on a transitioning element defeats any cross-fade or fade-out animation computed by the transition system. After writing any "apply default state to remaining elements" loop, list every transition/animation data structure in the parent frame/state object and verify the loop checks each one before applying the default.
50. **Type-usage consistency for JSDoc interfaces:** When a class field or method parameter has a JSDoc `@type` annotation defining an interface shape (e.g., `{ getTabForNode(nodeId: string): any }`), every property access and method call on that value in the implementation must appear in the declared type. If the code accesses `this.#bridge.nodeToTab` but the `@type` for `#bridge` only declares `getTabForNode()`, the type contract is incomplete -- any caller satisfying only the declared type will throw `TypeError` at runtime on the missing member. After writing code that uses a typed dependency, compare every `.property` and `.method()` usage against the JSDoc type declaration. If a member is missing from the type, add it. Similarly, update `@param` types on any setter method (e.g., `setTabBridge`) that accepts the dependency to include all accessed members.
51. **Conditional-skip side-effect preservation:** When a method gates a complex operation (animation, multi-step workflow) behind a condition (threshold check, feature flag, mode guard), the condition must only gate the *specific* operation, not unrelated side-effects that the spec requires regardless. If the spec says "if zoomed in, animate a zoom-out-and-back then focus the new child; otherwise, just focus the new child normally," the `if` branch animates-then-focuses and the `else` branch focuses directly. An early `return` that skips both the animation AND the focus change violates the spec — the focus change was unconditional. After writing any threshold/guard check with an early return, list every spec-required outcome of the enclosing method and verify each outcome is achieved on BOTH sides of the condition. The guard gates the mechanism (animation vs. instant), not the goal (e.g., focusing the child).
52. **Test layer matches gating layer:** When a task requires tests for threshold or conditional gating behavior (e.g., "animation triggers at zoom >= 0.9," "does not trigger when zoom < 0.9"), the tests must exercise the method that CONTAINS the gate — not a lower-level component that the gate controls. If the threshold check lives in `orchestrateZoom()` but the animation logic lives in `ZoomAnimator`, testing `ZoomAnimator` alone does not verify the gate. Write tests that call the gating method with inputs on both sides of the threshold and assert the downstream behavior (animation starts vs. does not start, focus changes vs. does not change). Testing only the inner component leaves the gate uncovered.
50a. **Test assertion-description alignment:** After writing each test, re-read the `it(...)` description and verify that at least one assertion directly tests the behavior described. If a test is titled "exits degraded mode after N fast frames", there must be an assertion like `expect(isDegraded).toBe(false)` — asserting `toBe(true)` only proves entry, not exit. A test whose assertions verify only a precondition or setup state, not the behavior in the title, is a test that doesn't test what it claims. Watch especially for paired state transitions (enter/exit, activate/deactivate, connect/disconnect): if the test title names one direction, the assertion must verify that direction, not the other. If you find you cannot assert the described behavior (e.g., the test harness can't simulate the exit condition), either fix the harness or delete the test — a test that cannot assert its claim is worse than no test because it provides false coverage.
51a. **Per-entity vs global state scope:** When a spec qualifies a threshold or condition per entity ("any animation that has been running for more than 2 frames", "each node that exceeds N pixels", "a tab that has been idle for M seconds"), the tracking state must be per-entity — not a single global counter or timestamp. A global counter like `systemFrameCount > 2` does not tell you how long *each individual entity* has existed. An entity created after the global counter already exceeds the threshold is immediately affected on its first frame (0 frames of running), violating the per-entity qualifier. Conversely, entities that existed before the tracking began may be incorrectly exempted. When you see "any X that has been Y for N", ask: "does my implementation track Y separately for each X?" If the answer is a single system-wide value, redesign to use per-entity state (e.g., a `Map<entityId, frameCount>` or a `startFrame` field on each entity).

53. **Animation-start timestamp anchor:** When ANY code path starts or resumes a frame-based animation that computes `deltaMs = now - lastTime`, and the animation loop was not already running, the `lastTime` value is stale — it was last set during the previous animation's final frame, which could be hundreds of milliseconds or seconds ago. The first frame computes a massive `deltaMs` and applies many frames' worth of change in a single frame — a visual discontinuity. Before calling `markDirty()` or requesting the first frame, reset the animation timestamp anchor to `performance.now()`. This applies to ALL animation-start code paths, not just delayed callbacks:
   - **Delayed callbacks:** `setTimeout`, `debounce`, `requestIdleCallback` that start animation.
   - **Event handlers:** `mouseUp` starting momentum, `keyDown` starting an animation, `scroll` initiating inertia. Even though the handler fires synchronously, the user may have paused (e.g., held the mouse still mid-drag), so no animation frames ran and the timestamp froze.
   - **State transitions:** Any code that checks `isActive` after calling a `.release()`, `.start()`, or `.onRelease()` method and then calls `markDirty()` to begin the animation loop.
   The pattern: set `lastTime = performance.now()` then `markDirty()`. Compare `#scheduleMomentumRelease()` which correctly resets `this.#animationLastTime = performance.now()` before `markDirty()`. A `markDirty()` that starts a new animation without a preceding timestamp reset is a bug. Run `scripts/check-animation-anchor.sh` to verify.
54. **Test assertion fidelity:** Every test's assertions must actually verify the behavior described in its `it()` / `describe()` title. A test titled "zoom level remains clamped during momentum" that only asserts `delta > 0` does not test clamping — it tests sign. After writing a test, re-read the test title and ask: "If the behavior described in the title were broken, would this test fail?" If the answer is no, the assertions are off-topic. For boundary/clamping tests, exercise inputs that push past the boundary and assert the output is constrained. For "does not trigger" tests, assert the specific non-occurrence (e.g., `isActive` is `false`), not just a side-effect direction. The test title is a contract — the assertions must fulfill it.

56. **Coordinator bypass consistency:** When any code path directly manipulates state that is managed by a coordination layer (e.g., AnimationCoordinator), it MUST also update the coordinator's bookkeeping. The most common instance: skip-to-end or degraded-mode code that jumps animation state to its final value by directly setting properties (e.g., `zoom.focusPoint = endFocus; this.#animation = null`) without cancelling the coordinator registration for that property. The coordinator's adapter captured a closure reference to the animation object at registration time -- nulling the local field does not invalidate the captured reference. On the next `coordinator.tick()`, the adapter uses the stale captured reference to compute an intermediate value and overwrites the final state. The fix: before or after directly setting final state, call `coordinator.cancel(property)` or `coordinator.cancelAll()` to remove the stale adapter. This applies to any coordinator/registry pattern, not just animations. After writing any code that bypasses a coordinator to directly manipulate managed state, ask: "Does the coordinator still have a registration that will overwrite this state on its next tick?" If yes, cancel it. Run `scripts/check-coordinator-bypass.sh` to verify.

57. **Staggered concurrent registration in tests:** When a class accepts multiple concurrent registrations, subscriptions, or entities that share mutable state (timestamps, counters, accumulators), tests MUST include at least one staggered-timing scenario — not just simultaneous registration. If a shared field like `lastTickTime` is written by `register()`, a test that registers two entities at the same clock time will not detect corruption when one entity registers mid-cycle. Write at least one test where the fake clock advances between registrations, then verify that pre-existing entities receive correct deltas on the next tick. Concrete example: register animation A at t=0, tick at t=16 (A gets 16ms), advance clock to t=20, register animation B, tick at t=36 — assert A gets 20ms (not 16ms). Simultaneous-registration tests verify the easy case; staggered registration is where shared-state corruption hides. After writing any concurrent-entity test suite, ask: "Do any of my tests advance the clock between entity registrations?" If no, add one.

58. **Dual-path value equivalence:** When branching logic computes the same user-visible value via different code paths for different data states (e.g., active vs. inactive, loaded vs. summary, cached vs. live), verify both paths produce identical results for identical inputs. Semantic differences between computation methods are invisible at the call site. Common trap: `collection.length` vs. a cached count field where one includes the element itself and the other does not (e.g., `getDescendants(id).length` counts root + descendants, while `descendantCount` counts only descendants -- the same branch shows different page counts depending on which path runs). After writing any `if/else` or ternary that computes the same output via different methods, ask: "If I had a branch in both states, would the displayed value be identical?" If not, determine which computation matches the spec definition and use it on both paths -- or normalize the values so they agree.

59. **Callee precondition verification:** When a caller routes to a method that enforces preconditions (throws on invalid state), the caller's guard condition must guarantee ALL of those preconditions -- not just approximate them. Read the callee's implementation and list every condition that triggers a `throw`. Then verify the caller's `if` statement ensures none of those conditions are met. Common trap: a callee throws when `target.childIds.length > 0`, but the caller only checks `id !== activeId` -- which is a different (insufficient) proxy for the same intent. Also consider what the guard produces when state fields are in their initial/null/zero value. If `activeBranchId` is `null` at startup, `branchId !== activeBranchId` is always true -- every branch looks inactive, including ones that already have children loaded. After writing any call to a method that throws, list the callee's preconditions and verify the caller's guard is equivalent to them, not just correlated.

55. **Time-windowed data expiry at consumption:** When a module collects time-windowed samples (e.g., drag velocity samples kept for the last 150ms), samples must be validated for freshness at BOTH collection time AND consumption time. Collection-time trimming (removing old samples when new ones arrive) is not sufficient — if the producer stops producing (e.g., the user holds the mouse still), no new samples trigger trimming, and stale samples persist silently. At consumption time (e.g., `release()` computing velocity), check whether the most recent sample's wall-clock age exceeds the time window. If it does, clear or ignore all samples — they represent motion that the user visually stopped. This requires either storing wall-clock timestamps per sample or accepting a `now` parameter at the consumption call site. The pattern: `if (now - lastSampleTimestamp > WINDOW_MS) { samples = []; }` before computing from samples. A consumer that computes from stale samples produces phantom motion.
